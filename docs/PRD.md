# PRD: 개인용 할 일 관리 앱

- 작성일: 2026-10-01
- 상태: 초안 (승인됨)
- 대상 사용자: 본인 1명 (개인용)

## 1. 배경 및 목표

하루 10~20개 정도의 할 일을 가볍게 기록하고, 완료 여부와 진행 정도를 한눈에 확인하는 개인용 웹 앱을 만든다. 설치나 서버 없이 브라우저에서 바로 열 수 있고, 새로고침해도 데이터가 유지되어야 한다.

### 목표
1. 할 일을 빠르게 추가·수정·삭제·완료 체크할 수 있다.
2. 업무/개인/공부 카테고리로 분류해 볼 수 있다.
3. 선택한 날짜의 진행률(전체/카테고리별)을 즉시 확인할 수 있다.
4. 새로고침·브라우저 재시작 후에도 데이터가 유지된다.
5. 빌드 도구와 프레임워크 없이 순수 JavaScript로 구현한다.

### 비목표 (범위 밖)
- 로그인, 서버, 클라우드 동기화, 다중 기기 지원
- 알림/푸시, 반복 일정, 우선순위, 태그
- 다크모드, 내보내기/가져오기 (향후 고려 항목 참조)

## 3. 기능 요구사항

### 3.1 할 일 추가 (FR-1)
- 제목(필수, 최대 100자)과 카테고리(기본값: 마지막으로 선택한 카테고리)를 입력해 추가한다.
- 현재 선택된 날짜에 추가된다.
- 공백만 있는 제목은 추가되지 않는다.

### 3.2 할 일 수정 (FR-2)
- 항목의 제목을 클릭(또는 편집 버튼)하면 인라인 편집 모드가 된다.
- Enter 또는 포커스 이탈 시 저장, Esc 시 취소한다.
- 카테고리도 항목에서 변경할 수 있다.

### 3.3 할 일 삭제 (FR-3)
- 삭제 버튼 클릭 시 확인창 없이 즉시 삭제한다.
- 삭제 직후 일정 시간(약 5초) 동안 "실행 취소" 알림을 보여준다.

### 3.4 완료 체크 (FR-4)
- 체크박스로 완료/미완료를 토글한다.
- 완료 항목은 취소선과 흐린 색으로 표시한다.

### 3.5 카테고리 (FR-5)
- 카테고리는 **업무 / 개인 / 공부** 3종 고정이다.
- 필터: 전체 / 업무 / 개인 / 공부. 필터는 목록 표시에만 영향을 준다.
- 카테고리마다 색상 구분을 둔다.

### 3.6 날짜 이동 (FR-6)
- 기본 화면은 오늘 날짜이다.
- 전날 / 오늘 / 다음날 버튼으로 이동하고, 날짜 선택기로 임의 날짜로 이동할 수도 있다.
- 날짜는 로컬 시간대 기준 `YYYY-MM-DD`로 다룬다.

### 3.7 진행률 (FR-7)
- 선택한 날짜 기준 **완료 수 / 전체 수**와 퍼센트를 진행률 바로 표시한다.
- 카테고리별(업무/개인/공부) 진행률도 함께 표시한다.
- 해당 날짜에 항목이 없으면 "할 일이 없습니다"로 표시하고 0%로 계산하지 않는다(0으로 나누기 방지).
- 진행률은 카테고리 필터와 무관하게 해당 날짜 전체를 기준으로 한다.

### 3.8 미완료 이월 (FR-8)
- "다음 날로 이월" 버튼은 선택한 날짜의 미완료 항목을 다음 날짜로 이동한다.
- 이월은 자동이 아니라 사용자가 수동으로 실행한다.

## 4. 데이터 모델

### Todo
| 필드 | 타입 | 설명 |
|------|------|------|
| `id` | string | 고유 ID (`crypto.randomUUID()`, 미지원 시 시각+난수) |
| `title` | string | 제목 (1~100자) |
| `category` | `"work"` \| `"personal"` \| `"study"` | 카테고리 |
| `date` | string | `YYYY-MM-DD` |
| `done` | boolean | 완료 여부 |
| `createdAt` | number | 생성 시각 (epoch ms) |

### 저장 형식
`localStorage` 키 `todo-app:v1`에 아래 JSON을 저장한다.

```json
{ "version": 1, "todos": [ { "id": "...", "title": "...", "category": "work", "date": "2026-10-01", "done": false, "createdAt": 1790000000000 } ] }
```

## 5. 비기능 요구사항

| 항목 | 요구사항 |
|------|----------|
| 실행 | `index.html`을 더블클릭하거나 정적 호스팅으로 열면 동작한다. 빌드·설치 불필요 |
| 지속성 | 변경 시마다 즉시 저장한다. 새로고침 후 데이터 유지 |
| 성능 | 하루 20개(전체 수천 개까지) 항목에서 조작 후 즉시(체감 지연 없음) 반영된다 |
| 오류 처리 | 저장 실패(용량 초과, 저장소 차단)나 손상된 JSON 시 앱이 죽지 않고 안내 메시지를 표시한다. 손상 데이터는 덮어쓰기 전에 별도 키로 백업한다 |
| 보안 | 사용자 입력은 `textContent`로 렌더링해 XSS를 방지한다 (`innerHTML`에 입력값 직접 삽입 금지) |
| 접근성 | 키보드만으로 추가·체크·삭제 가능, 체크박스·버튼에 레이블, 충분한 색 대비 |
| 호환성 | 최신 Chrome / Edge / Firefox / Safari |
| 반응형 | 데스크톱과 모바일 폭(약 360px 이상)에서 사용 가능 |

## 6. 화면 구성

단일 페이지, 위에서 아래로 다음 영역을 배치한다.

1. **헤더**: 앱 이름, 날짜 이동(◀ 날짜 ▶ / 오늘 / 날짜 선택기)
2. **진행률**: 전체 진행률 바 + 퍼센트(`완료 n / 전체 m`), 카테고리별 미니 진행률
3. **입력 영역**: 제목 입력창, 카테고리 선택, 추가 버튼
4. **필터 탭**: 전체 / 업무 / 개인 / 공부
5. **할 일 목록**: 체크박스, 제목(인라인 편집), 카테고리 배지, 삭제 버튼
6. **하단 액션**: "다음 날로 이월" 버튼, 실행 취소 알림(토스트)

## 7. 기술 구성

- 파일: `index.html`, `style.css`, `src/state.js`, `src/storage.js`, `src/view.js`, `src/app.js` (프레임워크·번들러·외부 의존성 없음). `file://`로 열어도 동작하도록 ES 모듈 대신 일반 `<script>` 태그를 의존 순서대로 로드한다.
- 코드는 세 가지 책임으로 나눈다.
  - **저장소(storage)**: `load()`, `save(todos)` — localStorage 입출력과 버전·오류 처리만 담당
  - **상태(state)**: 할 일 CRUD, 날짜별·카테고리별 조회, 진행률 계산, 이월 — DOM을 알지 못하는 순수 로직
  - **화면(view)**: 상태를 DOM으로 렌더링하고 이벤트를 상태 호출로 연결
- 데이터 흐름: 사용자 이벤트 → 상태 변경 → 저장 → 재렌더링 (단방향)
- 순수 로직(진행률 계산, 이월, 날짜 처리)은 DOM과 분리해 단위 테스트가 가능하게 한다.

## 8. 성공 기준

검증일 2026-10-01, 내장 브라우저(Chromium) + 로컬 정적 서버 기준.

- [x] 20개 항목을 추가해도 조작 지연이 체감되지 않는다. (하루 20개: 체크 1.3ms·추가 0.7ms, 3,001개 저장 상태: 3.9ms·3.2ms. 스크립트 실행 시간이며 화면 페인트는 제외)
- [ ] 새로고침·브라우저 재시작 후 데이터가 100% 유지된다. (새로고침 후 유지는 확인, **브라우저 재시작은 미확인**)
- [x] 추가와 완료 체크가 각각 2번 이내의 조작(입력+Enter, 클릭 1회)으로 가능하다.
- [x] 진행률이 추가/삭제/체크/이월 시 항상 정확히 갱신된다 (항목 0개일 때 오류 없음). (샘플 20개를 손으로 계산한 값과 대조: 25%, 업무 2/7·개인 2/7·공부 1/6)
- [x] 손상된 저장 데이터나 저장소 차단 상태에서도 앱이 열리고 안내를 보여준다. (전체 손상, 일부 손상, 저장소 차단, 저장 실패 4가지 확인. 차단·실패는 저장소 접근을 막는 코드를 주입한 iframe으로 시뮬레이션)

## 9. 테스트 계획

- **테스트 실행**: Node 없이 `tests/index.html`을 브라우저로 열어 확인한다 (탭 제목이 `PASS n/n`이면 통과). 상대 경로 스크립트가 로드되도록 로컬 정적 서버(예: `python -m http.server`)로 여는 것을 권장한다.

- **브라우저 확인**: Chrome/Edge/Firefox에서 동작, 모바일 폭 레이아웃 확인

## 11. 열린 질문

요구사항에 대한 열린 질문은 없다. 위 내용은 2026-10-01 합의된 기본값을 따른다. 아래는 구현·검증 후 남은 사항이다.

**미검증**
- `index.html`을 더블클릭(`file://`)해서 여는 실행. 일반 `<script>`만 사용하도록 설계했지만 직접 확인하지 못했다. (검증 환경이 `file://` 페이지를 정적 스냅샷으로 열어 스크립트가 실행되지 않음)
- Chrome 계열 외 브라우저(Firefox, Safari)와 실제 모바일 기기의 터치 조작. 360px 폭의 레이아웃만 확인했다.
- 브라우저를 완전히 종료했다가 다시 연 뒤의 데이터 유지.
- 스크린 리더와 키보드만으로 하는 전체 흐름. 제목 편집(Enter 저장, Esc 취소)과 `aria-label`은 확인했다.

**알려진 한계**
- 한 항목을 편집하는 도중에 다른 항목의 제목을 바로 클릭하면, 첫 클릭은 앞선 편집을 저장하는 데만 쓰여 한 번 더 눌러야 한다. 저장 시 목록 전체를 다시 그리기 때문이다.
